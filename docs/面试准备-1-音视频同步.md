# 面试准备：音视频同步

## 一、架构总览

```
┌─────────────┐     ┌──────────────┐     ┌──────────────────┐
│ AudioOutput │     │  AVSyncClock │     │ videoRenderThread │
│ (SDL回调)   │────→│  (无锁共享)  │←────│  (渲染线程)       │
└─────────────┘     └──────────────┘     └──────────────────┘
  set_audio_clock()       ↕                calc_display_delay()
                   std::atomicneed_force_catch_up()
```

**核心思想**：音频回调驱动 `audio_clock` 前进，视频渲染线程每取到一帧就拿当前 `audio_clock` 做对比，决定"等多久"或"丢不丢"。

---

## 二、三种同步模式

| 模式 | 场景 | 基准时钟 |
|------|------|----------|
| `AUDIO_MASTER` | 有音频+有视频 | 音频 PTS（SDL 回调推进） |
| `VIDEO_MASTER` | 只有音频、无视频 | 无需同步 |
| `SYSTEM_MASTER` | 只有视频、无音频 | `av_gettime()` 系统单调时钟 |

模式选择代码位于 `PlayerCore::open()` 中，根据 `demuxer_->hasAudio()` 和 `demuxer_->hasVideo()` 决定。

---

## 三、核心常量（必须背住）

```cpp
MIN_SYNC_THRESHOLD= 10ms// 小于此值 → 正常渲染
MAX_SYNC_THRESHOLD    = 100ms   // 大于此值 → 触发帧倍延/提前
NOSYNC_THRESHOLD      = 10s     // 超过此值 → 不做同步（异常状态）
SYNC_FRAMEDUP_THRESHOLD = 100ms // delay > 此值时用 delay+diff（而非 2×delay）
LAG_THRESHOLD         = 1s      // 累计落后超过 1s
LAG_CONTINUE_COUNT    = 10      // 且连续 10 帧 → 强制丢帧
MIN_REFRSH_US         = 1ms// 最小刷新间隔（下限）
```

---

## 四、`calc_display_delay` 核心算法（AUDIO_MASTER 模式）

```
输入: video_pts_us（当前帧 PTS，微秒）
输出: delay（本帧应等待的微秒数）

1. last_pts = 上一帧 PTS
2. delay = video_pts_us - last_pts// 帧间距
3. 若 delay ≤ 0 或 > 1s → 用上一次的 delay
4. diff = video_pts_us - audio_clock// 音画差
5. sync_threshold = clamp(delay,10ms, 100ms)

6. 分支判断:
   if |diff| > 10s → 不处理（异常值跳过）
   elif diff< -sync_threshold → 视频落后 → delay = max(0, delay + diff)  // 加速
   elif diff > +sync_threshold → 视频超前 →
       if delay > 100ms → delay = delay + diff  // 大延迟：加上整个diff
       else → delay = delay × 2                  // 小延迟：倍延

7. frame_timer += delay
8. actual_delay = frame_timer - current_time
9. return max(actual_delay, 1ms)
```

**用人话说**：
- 视频落后音频 → 减少等待，赶紧显示
- 视频超前音频 → 增加等待，等音频跟上
- 严重落后（>1s 且连续 10 帧）→ 丢帧不渲染

## 五、`need_force_catch_up` 丢帧机制

```cpp
bool need_force_catch_up() const {
    return (last_pts - audio_clock) < -LAG_THRESHOLD   // 落后 >1s
        && lag_count >= LAG_CONTINUE_COUNT;             // 且连续 10 帧
}
```

在 `videoRenderThreadFunc` 中：
```cpp
if (sync_clock_->need_force_catch_up()) {
    GlobalPool::getFramePool().recycle(frame);  // 回收帧内存
    continue;  // 跳过渲染
}
```

## 六、SYSTEM_MASTER 模式（纯视频）

无音频时无法用音频时钟，改用系统时钟 `av_gettime()`：

```
1. 首帧: system_base = now - video_pts  → 建立基线
2. 后续帧:
   delay = (video_pts - last_pts) / speed
   new_timer = frame_timer + delay
   actual_delay = new_timer - now
```

**暂停恢复问题**：暂停期间 `av_gettime()` 仍在走，恢复后会导致所有帧瞬间播完。

**解决方案**：`pause()` 记录暂停时刻，`resume()` 计算暂停时长累加到 `m_total_pause_us`，`getCurrentSystemClock()` 返回 `(now - base) - total_pause_us`。

---

## 七、倍速播放

```cpp
void setSpeedRatio(double ratio) { m_speed = ratio; }
```

仅在 SYSTEM_MASTER 模式下生效：`delay /= m_speed`。

AUDIO_MASTER 模式下，倍速由音频侧`SDL` 的重采样变速控制，视频自然跟随音频时钟。

## 八、跨线程通信设计

```
AudioOutput（SDL 回调线程）──atomic store──→ m_audio_clock
                ↓ atomic load
                            VideoRenderThread ←─────┘
```

**为什么用 atomic 而不用 mutex？**
- SDL 音频回调是实时线程，**绝对不能阻塞**（否则爆音）
- `std::atomic<int64_t>` + `memory_order_release/acquire` 保证可见性，无锁零开销
- 视频线程读到的是"最终一致"的值，延迟最多一帧（16ms@60fps），音视频同步阈值 10ms 以上，完全可接受

## 九、开发中遇到的问题

### 问题 1：暂停恢复后音画剧烈漂移

**现象**：暂停 10 秒后恢复，视频画面快速刷过10秒的帧才恢复正常。

**原因**：SYSTEM_MASTER 模式下，`av_gettime()` 在暂停期间仍然递增，恢复后 `frame_timer` 远落后于当前时间，`calc_display_delay` 返回 0，所有帧瞬间被渲染。

**解决**：新增 `pause()`/`resume()` 方法 + `m_total_pause_us` 累计暂停时长，`getCurrentSystemClock()` 扣除暂停时间。

### 问题 2：Seek 后画面卡在旧帧

**现象**：拖动进度条后，画面停在旧位置 1~2 秒才跳转。

**原因**：Seek 时 `video_frame_queue_` 里还有旧帧未消费完，新帧被追加到队尾。

**解决**：Seek 时 `video_frame_queue_->Flush()` 清空队列，并`sync_clock_->reset()` 重置所有时钟状态，让首帧以当前时刻为新基线。

### 问题 3：2×倍速下视频"一卡一卡"

**现象**：2 倍速播放时画面不流畅，但音频是正常 2 倍速。

**原因**：AUDIO_MASTER 模式下，音频时钟以 2倍速推进，但`calc_display_delay` 计算出来的 delay仍然是帧间距（如 33ms），导致视频来不及"消费"帧而频繁触发 lag丢帧。

**解决**：在帧间距计算后不额外除以 speed（因为 audio_clock 已经在加速），让 diff 值自然驱动追赶逻辑。只在 SYSTEM_MASTER 模式下才`delay /= m_speed`。

### 问题 4：lag_count 不归零导致正常帧被误丢

**现象**：快进后恢复正常播放，偶尔出现丢帧导致画面跳跃。

**原因**：`lag_count` 在 diff恢复正常时没有清零，历史累计值使`need_force_catch_up()` 一直为 true。

**解决**：在 `diff > +sync_threshold`（视频超前）分支中显式 `lag_count = 0`，恢复正常后立即清零。

## 十、面试必答题

### Q1：为什么选音频为主时钟而不是视频？
> 人耳对音频断续极其敏感（破音/卡顿），但对视频丢1~2 帧几乎无感知。所以让音频匀速输出，视频去跟音频。

### Q2：atomic 的memory_order 为什么用 release/acquire 而不是 seq_cst？
> `seq_cst` 有全局排序开销（在 x86 上是 MFENCE），`release/acquire` 只保证 store-load 对的可见性，性能更好。对时钟这种单写者-单读者场景足够。

### Q3：为什么阈值是 10ms 和 100ms？
> 10ms 约等于 1帧 @100fps，肉眼不可见；100ms 是人耳能感知"嘴形不对"的临界值。低于 10ms 不需要调整（浪费精度），高于 100ms 必须积极追赶。

### Q4：如果网络视频 PTS 乱序怎么办？
> 代码中 `if (delay <= 0 || delay > 1000000) delay = last_delay;` 处理了乱序和跳变：用上次的正常帧间距兜底，防止负delay 或巨大 delay。

### Q5：如果音频 PCM 输出不均匀（SDL 回调频率抖动）怎么办？
> audio_clock 是按实际输出的 PCM 采样数折算的 PTS，不依赖回调频率。SDL 回调多给了就多算，少给了就少算，始终准确反映"已经播出的音频对应的时间点"。
